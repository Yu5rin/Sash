# リリース手順

Sash の配布物（Windows 向けの単一 exe）を作り、GitHub Release として公開するまでの手順です。
リリースは **`.github/workflows/release.yml`（Actions の「リリース」）が正規の経路**で、
`v` で始まるタグを push すると、テスト・発行・配布物の検査・照合値ファイルと `latest.json` の作成・
リリース本文の組み立てまでを Linux ランナー上で行い、GitHub Release を**下書き**として作ります。
人が行うのは、変更履歴を書くこと、タグの push、下書きを確かめて「Publish」を押すことだけです
（Graft・Pane と同じ流れ）。

`tools\New-Release.ps1` は手元で配布物を試すための道具で、リリースの経路としては使いません。

## 手順

1. **`main` を最新にして、出したい版になっているか確かめる**

   `Directory.Build.props` の `<Version>` が出したい版であることを確認します。
   タグと `<Version>` が食い違うと、ワークフローは「版の確認」で止まります。

   ```powershell
   cd C:\Users\YUGO\Sash
   git checkout main
   git pull origin main
   Select-String -Path Directory.Build.props -Pattern '<Version>'
   ```

   版を上げる場合は、`<Version>` を書き換え、`docs/変更履歴.md` の先頭に「## <版>」の節を足して、
   プルリクエスト経由で `main` に入れてから次へ進みます。

2. **タグを作って push する（これでワークフローが走る）**

   ```powershell
   cd C:\Users\YUGO\Sash
   git tag -a v<バージョン> -m "Sash <バージョン>"
   git push origin v<バージョン>
   ```

   タグは `v1.2.3` の形にします（更新処理が解釈できる形。3点区切り）。

3. **Actions の「リリース」の進行を確かめる**

   [Actions](https://github.com/Yu5rin/Sash/actions) を開き、「リリース」が次の順に進んで緑になることを確認します。

   版の確認 → UI のテストとビルド → テスト → Windows 向けに発行 → 配布物を置いて中身を確かめる →
   照合値ファイルを作る → latest.json を作る → リリース本文を組み立てる → リリースを作成（下書き）

   途中で赤くなったら、下書きは作られません。ログの該当の段を読んで原因を直します。

4. **作られた下書きを確かめて「Publish」を押す**

   [Releases](https://github.com/Yu5rin/Sash/releases) に「Draft」として現れるリリースを開き、
   次を確かめてから公開します。公開は人が押す決まりです（ワークフローは `draft: true` で作ります）。

   - 添付が3件ある：`Sash-<バージョン>-win-x64.exe`、照合値ファイル `Sash-<バージョン>-win-x64.exe.sha256`、
     社内配布用の `latest.json`
   - タイトルがタグと同じ `v<バージョン>` になっている（「Sash 0.1.0」のような書き方はしない）
   - 本文が `## 変更点` と `## ダウンロード` の2節だけで、最後に README への案内が1行ある
   - 変更点が、その版の分だけ、利用者向けの日本語で書かれている

   公開すると、利用者の Sash が新しい版を見つけるようになります（下書きのうちは見つかりません）。

5. **社内の共有フォルダに配る場合**

   公開したリリースから exe をダウンロードし、`tools\Publish-Internal.ps1` で共有フォルダに置きます
   （詳しくは [更新と社内配布.md](更新と社内配布.md)）。

   ```powershell
   cd C:\Users\YUGO\Sash
   powershell -ExecutionPolicy Bypass -File tools\Publish-Internal.ps1 -Exe "$env:USERPROFILE\Downloads\Sash-<バージョン>-win-x64.exe" -Destination \\fileserver\tools\Sash
   ```

## 手元で試すとき

リリースには使いませんが、配布物を手元（Windows）で確かめたいときは `tools\New-Release.ps1` が使えます。
UI のビルド・発行・照合値ファイル・本文の下書きまでを1コマンドで行います。

```powershell
cd C:\Users\YUGO\Sash
powershell -ExecutionPolicy Bypass -File tools\New-Release.ps1
```

- 配布物：`publish\release\Sash-<バージョン>-win-x64.exe` と `.sha256`
- 本文の下書き：`publish\release\リリース説明.md`（`docs\リリース説明_テンプレート.md` に、
  `docs\変更履歴.md` の該当する版の節と、ファイル名・サイズ・SHA256 の表を差し込んだもの）

**ここで作った配布物や本文を、GitHub Release へ添付・貼り付けて公開しないでください。**
手元で作った exe は、ワークフローが作る exe とバイト単位で一致しません。本文の表の SHA256 を手で貼ると、
添付と食い違う原因になります。

## 注意点

### リリース本文は「変更点」と「ダウンロード」だけ

リリース本文に置く見出しは `## 変更点` と `## ダウンロード` の2つだけにし、その版の変更の小見出しは
`###` 以下にします。インストール・更新の方法、主な機能、動作環境などの版をまたいで変わらない説明は
README に置き、リリース本文には繰り返しません。その版へ上げるときだけ必要な注意は、`###` の小見出しとして
変更点の中に書きます。

### 添付の名前と照合値ファイルの書式を変えない

アプリの更新処理（`src/Sash.Core/Update/`）は、リリース本文もタイトルも読みません。Atom フィードから
タグを読み、次の規則で URL を組み立てます。

- タグは `v1.2.3` の形（`UpdateVersion` で解釈できる形）にする
- exe の名前は `Sash-<タグから v を除いた版>-win-x64.exe` にする（`UpdateSource.AssetFileName`）
- 照合値ファイルの名前は exe 名に `.sha256` を付け、中身は `sha256sum` と同じ書式の1行
  （`<64桁の小文字16進>  <ファイル名>`）にする（`UpdateFeedLogic.ParseChecksum`）。照合値が取れないとき、
  アプリは入れ替えない

公開後に添付を差し替えたり消したりしないでください。

### ダウンロード表の SHA256 は手で書かない

本文の「## ダウンロード」の表は、ワークフローが添付する exe そのものから計算します。手で書いたり、
別の環境でビルドしたもののハッシュを貼ったりしないでください（Graft で実際に食い違いの事故が起きたため、
ワークフローに一本化しています）。本文を直したいときは、表には触れず、「## 変更点」の部分だけを直します。

### タグ push と手作業を二重に走らせない

タグを push したら、手作業で配布物を作って同じリリースへ添付する経路は使わないでください。
同じ版の配布物が複数並ぶ事故の元になります。

### コード署名をしていない

Sash にはコード署名証明書を付けていません。ダウンロードした `Sash-<バージョン>-win-x64.exe` を実行すると、
Windows の SmartScreen が「Windows によって PC が保護されました」と表示します。
内容を確認のうえ「詳細情報」→「実行」で起動できます。
